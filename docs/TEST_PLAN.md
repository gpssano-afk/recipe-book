## 1. 方針・環境

- 純粋なvalidator、検索、日付、ルーレット、容量計算は単体テスト。乱数と日付は注入して境界値を再現する。
- repositoryはfake-indexeddbで結合テストし、Blob保存・実際の容量制限・トランザクション・versionchangeは実Chromeで検証する。
- 主要な利用フローはPlaywrightで実ブラウザE2E。Android Chrome実機で片手操作、撮影/ファイル選択、インストール、オフライン再起動、大容量復元を確認する。
- PCのモバイルエミュレーションだけでAndroid実機試験を代用しない。開発用サーバーの確認だけで本番のPWA試験を代用しない。
- 実行環境、OS、Chrome、アプリコミット、DB版、fixture版、実行日時、期待/実結果、証跡を記録する。

対象画面サイズ：320×568、360×800、390×844、430×932、横向き800×360、タブレット768×1024 CSS px。文字200%拡大、Android標準/大きい文字設定、ソフトキーボード表示、TalkBack、片手のタップも確認する。主対象Chromeの版は実行時に記録し、特定の未確認バージョンを動作保証しない。

## 2. Fixture

すべて架空・自作のデータを使う。外部サイトのレシピ全文や家庭写真をテスト用にコミットしない。

| データ集合 | 内容 |
| --- | --- |
| Empty | 0レシピ、0画像、0履歴 |
| Small | 6カテゴリ、料理名重複、タグ表記揺れ、本文なし、URLだけ、画像なしを含む12件 |
| Media | JPEG/PNG/WebP、縦向きEXIF、透明画像、スクリーンショット、6枚添付、表紙あり/なし |
| History | 同日複数調理、過去日、決定のみ、紐付く調理、改名後の決定、直近決定が候補外 |
| Limits | 1,000レシピ、各履歴20,000件、画像容量40MiB直前、非画像8MiB直前等を個別に構成 |
| Invalid | 型違い、欠損、未来版、重複ID、孤児参照、不正URL、不正base64、偽MIME、巨大画像、破損JSON |
| Migration | 将来スキーマ変更時に旧版DBとv1バックアップを固定fixtureとして追加 |

各上限テストは他の上限を超えないよう独立に用意する。バックアップの比較はレシピ/履歴/参照/画像の意味的内容を対象とし、出力日時・metaの差を除外する。

## 4. バックアップの詳細検証

T14〜T18では次を必ず含める。

- 表紙・料理写真・スクリーンショット・サムネイル・両履歴を含む往復。Phase 1の履歴空配列も読めること。
- 未知のformat、未来formatVersion、必須キー欠落、余分なキー、型不一致、重複ID、循環する/存在しない参照、別料理のdecisionId、複数履歴から同じ決定への参照。
- 不正な日時・未来の調理日・不正URL・列挙値・負数容量・declared size不一致、base64のpadding・余分な文字、MIME偽装・寸法詐称。
- ファイル選択前の容量判定、画像ヘッダ検査、画素数制限、1枚ずつの検証、深さ上限、巨大文字列の拒否でUIのフリーズを抑えられること。
- DB内の旧レコードを比較し、失敗後の件数だけでなく内容と画像が不変であること。トランザクションの失敗を握りつぶさないこと。
- バックアップ中の別タブ更新では一貫した旧スナップショットが出力され、新しい変更をバックアップ済みと誤認しないこと。
- ファイル生成・ダウンロード要求を「外部保管済み」と表示しないこと。初回登録の消失リスク案内と7日後のリマインドも確認する。

暗号化・署名がないため改ざんの本人性までは保証しない。構造上有効だが内容が変わったファイルは、利用者がプレビューして置換を判断する。

## 5. PWA・公開の詳細検証

Viteの開発モードではなくproduction buildを使う。サブパス `/recipe-book/` に相当する配信で、アセット、manifest、SW登録位置、開始URL、scope、詳細ルート再読み込みを確認する。本番URLでの確認は公開後に別途実施する。

オフラインでは一覧閲覧だけでなく、新規・編集・削除・画像表示・検索・定番・抽選・決定・調理履歴・出力・復元を操作する。ネットワークパネルで外部画像やCDNへの実行時依存がないことを確認する。まだインストールされていない画面chunkが必要にならないことも確認する。

アプリ更新で既存DBが保持されること、旧SWを使う別タブへ更新案内が出ること、端末のストレージ消去後は空の新規利用となりバックアップ以外から自動復旧できないことを確認する。

## 6. 性能・リリース判断

採用初期案の目標：1,000件のテキスト検索は代表実機で入力確定後500ms以内、写真一覧の初期表示は3秒以内（既存のローカルデータ）。画像処理は1枚ずつ行い、時間がかかる場合は処理中表示を出す。これらは未測定の目標であり達成済みではない。

64MiB近くのバックアップでクラッシュ/OS終了する場合は公開を止め、データ保持を優先して上限または方式を見直す。性能目標未達は測定条件と改善案を記録する。ブラウザ容量や永続保存許可は端末依存なので、特定容量が必ず使えるという合格基準にはしない。

重大なデータ消失、無確認上書き、破損復元、オフライン起動不可が残っていれば初期版公開不可。未実行の必須ケースは未実行のまま明示し、実機未検証をPASSに変えない。
