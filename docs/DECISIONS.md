# 設計判断・未確認事項

設計日：2026-10-12。対象：初期版、設計のみ。[README](../README.md) / [仕様](PRODUCT_SPEC.md) / [データ](DATA_MODEL.md) / [構成](ARCHITECTURE.md)

## 状態の意味

- **確定要件**：利用者の依頼で指定された制約。
- **採用初期案**：本設計で具体化した実装基準。実装を始めるために毎回承認を取り直す必要はない。変更は理由と影響を記録する。
- **未確認**：実機試験、サービス設定、最新の規約等による裏付けがまだない事項。
- **将来**：初期版の実装対象に含まない機能。

以下の判断を変更するときは既存の理由を消さず、日付・変更後の案・理由・影響する文書・データ移行の有無を追記する。

## D01 端末内保存の静的PWA

**確定要件**：React + TypeScript + Vite、GitHub Pages、IndexedDB、Android Chrome優先、初期版は1台、サーバー/ログイン/クラウドDB/有料APIなし。

運用費と保守負担を抑え、通信なしでもレシピを使える。代替のFirebase/Supabase等は共有・同期には有効だが、現在は認証・権限・費用管理の負担が不要。指定技術を変更する理由は現時点ではない。将来家族共有を入れる場合は別途設計する。

## D02 定番はお気に入りと同義

**採用初期案**：「佐野家の定番」= `isFavorite=true`。別フラグや独立コレクションを持たない。利用者がどちらへ登録するか迷わず、ホームから1タップでアクセスできる。将来「試したい」「定番」等を分けたい場合はタグまたは新たな状態の必要性を確認する。

## D03 決定と調理を分離

**採用初期案**：決定履歴と調理履歴を別storeにする。「これに決定」は作った事実ではないため、最近の調理除外を決定日で代用しない。スケジュール/予定日/献立セットまでは導入しない。決定の料理名はスナップショットを保持し、レシピの改名後にも当時の表示を残す。

レシピを削除した場合は関連履歴も削除する。過去履歴を孤立させて永続保存する代替案より、初期版の参照整合性と利用者が理解しやすい削除を優先する。削除確認で影響範囲を説明する。

## D04 単純な抽選と再抽選

**採用初期案**：条件で候補を絞って一様抽選し、直近決定・直前表示を避ける。複雑な重み、学習、栄養最適化は使わない。最近の調理除外は初期7暦日、ユーザーが変更できる。候補0件で勝手に条件を緩めず、1件なら再抽選できないことを伝える。

同じ2品しかない場合の再抽選では直近決定除外を緩め、今と違う料理を優先する。具体的な優先順位はPRODUCT_SPECのR08を正本とする。

## D05 入力は自由文中心、料理名だけでも登録可能

**採用初期案**：材料と分量を行で持ち、分量は自由文、人数は任意整数。手順は順序付き文字列。材料分解・単位変換は行わない。URLやスクリーンショットをまず保存して後から書き足せるよう、本文を必須にしない。

固定カテゴリは6つ・単一選択、柔軟な分類はタグで補う。タグマスタや多対多の結合storeは初期版に不要。料理名重複・同日の複数回調理は有効なデータとして許可する。

## D06 画像はBlob、ローカル圧縮、6枚まで

**採用初期案**：画像本体とサムネイルは別store内のBlobとして持つ。レシピ本文を検索するだけで画像をロードしない。料理写真とスクリーンショットは種別を分け、文字の可読性を優先した設定を用意する。

元画像を残す代替案は容量負担が大きいため不採用。元ファイルの再取得はできない旨を画像プレビューで説明する。HEIC変換ライブラリ、画像編集UI、OCRは導入しない。端末が未対応画像を返す場合はJPEG/PNG/WebPでの再選択を案内する。

## D07 バックアップは必須・全件置換

**確定要件**：ブラウザ保存に絶対的な永続性はない。写真付きバックアップを初期版に含める。

**採用初期案**：Phase 1にバックアップを前倒し、JSON/base64の単一ファイルと全件置換復元を採用する。理由はZIP追加依存・マージ競合・重複IDの扱いを初期版で増やさないため。base64の容量増とメモリ使用量は不利なので、全媒体40MiB、非画像部分8MiB、ファイル64MiBの上限を置く。保存可能な状態がバックアップで往復できる制約を設ける。

数値は**未確認の性能前提を含む採用初期案**。低メモリAndroidで検証し、遅延・強制終了が出るなら公開前に上限の見直しまたはストリーム形式への変更を設計する。上限を下げる変更では既存データが書き出せなくならない移行を先に用意する。

復元では検証済みデータを1トランザクションで置換し、失敗時は旧データを残す。チェックサムは誤改変の検出に役立つが署名・本人性の保証にはならず、初期版では形式・内容・参照・画像の検証を必須とする。バックアップは暗号化しないため保管場所へ注意を促す。

## D08 日付・ID・互換性

**採用初期案**：UUID v4、登録/更新/決定はUTC日時、調理日はローカル日付文字列。旅行やタイムゾーン変更で調理日がずれない。日時は端末時計に依存するため、競合制御は時刻だけでなくrevisionを使う。

DB_VERSIONとformatVersionは別管理。将来版はv1のバックアップを読み込める方針とし、旧アプリで新形式を読むことは保証しない。移行失敗時の自動初期化は禁止。履歴storeをPhase 1で用意してPhase 2でそのまま使う。

## D09 hashルーティングと確認型PWA更新

**採用初期案**：GitHub Pagesのサブパスで動くHashRouterを採用。History API + 404コピー方式より設定が単純。URLの `#` は許容する。

Service Workerはapp shellだけをキャッシュし、更新は利用者が保存を終えてから適用する。無条件autoUpdateは入力やDB互換性の事故につながるため採用しない。初回オフラインアクセスは非対応であることを明示する。

## D10 自動取り込みは将来

**確定要件**：初期版は外部検索・URL保存・手動入力を優先し、規約違反やアクセス制限回避を前提にしない。

**採用初期案**：初期検索サービスはGoogleへのリンクのみ。無料APIで本文を取り込む前提を置かない。JSON-LDはデータ形式でありCORS許可や転載許可を与えない。APIを利用する場合も認証、CORS、利用条件、保存制限を別々に検証する。

前回調査の資料・失敗した確認項目はARCHITECTUREへ記録した。今回の再開では外部Web検索を行わない。新しい調査が許可された将来タスクで必要な点だけ再確認する。

## D11 最小の保守構成

**採用初期案**：idb、React Router、vite-plugin-pwaを補助候補とし、通常のhooksと小さな純粋関数を中心にする。大規模な状態管理、汎用プラグイン、同期基盤は導入しない。テストでは保存・復元の失敗と参照整合性を優先し、単に実装を再現するテストを増やさない。
