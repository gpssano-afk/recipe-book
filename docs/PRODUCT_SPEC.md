## 1. 適用範囲と用語

**確定要件**：家庭用PWA「佐野家のごはん」。React・TypeScript・Vite、GitHub Pages、IndexedDBを基本に、Android Chromeの1台で利用する。サーバー、ログイン、クラウドDB、有料APIは使わない。保存済み情報のオフライン利用と写真を含むバックアップは初期版必須。

以下の具体的な数値・操作仕様は**採用初期案**。未確認事項は[DECISIONS](DECISIONS.md)に集約する。初期版は[ROADMAP](ROADMAP.md)のPhase 1〜4全体を指す。

| 用語 | 定義 |
| --- | --- |
| 佐野家の定番 | お気に入り `isFavorite=true` のレシピ。独立した別コレクションは作らない |
| 献立決定 | ルーレット結果を「これに決定」した事実。調理済みとは限らない |
| 調理履歴 | 利用者が「作った」を登録した日付・メモ |
| 添付 | 料理写真またはレシピのスクリーンショット。OCR・AI解析はしない |
| 保存済み | IndexedDBのトランザクションが完了した状態 |
| バックアップ | 写真を含む全データを1つのJSONファイルに出力したもの |

## 2. 共通ルール・入力契約

文字数はUnicodeコードポイント数。改行はLFへ統一し、文字列の前後の空白を除去する（本文内部の空白・改行は維持）。検索用正規化と保存文字列は分ける。空の任意文字列は `""`、未指定の数値・URL・参照は `null`、コレクションは空配列で統一する。

| 項目 | 必須・初期値 | 検証・上限 |
| --- | --- | --- |
| 料理名 | 必須 | 1〜100文字。重複名は許可し、自動統合しない |
| カテゴリ | 必須、その他 | 主菜、副菜、汁物、主食、デザート、その他のいずれか1つ |
| 材料・分量 | 任意、0行 | 最大100行。材料名1〜100文字、分量0〜100文字（「適量」「大さじ1/2」等の自由文） |
| 人数 | 任意、未指定 | 整数1〜100人。空欄を0へ変換しない。分量の自動換算なし |
| 手順 | 任意、0件 | 最大100件、1件1〜2,000文字。配列順を手順番号にする |
| 調理時間 | 任意、未指定 | 整数1〜1,440分。準備を含む目安。タイマー機能なし |
| メモ | 任意 | 最大5,000文字 |
| タグ | 任意 | 最大20個、1個1〜30文字。正規化後の同一タグは統合し最初の表記を残す |
| 元URL | 任意 | 最大2,048文字。絶対URL、`http:` / `https:` のみ。ユーザー名・パスワード入りURL、制御文字を拒否 |
| お気に入り | false | 詳細・一覧・編集から切り替え可能 |
| 添付 | 任意 | 1レシピ合計6枚まで。画像要件は後述 |
| 登録日・更新日 | 自動 | UTC ISO 8601日時。表示は端末のローカル時刻 |
| 調理日 | 当日の端末日付 | 実在する `YYYY-MM-DD`、1900-01-01〜端末の今日。未来日を拒否 |
| 調理メモ | 任意 | 最大1,000文字 |
| 検索語 | 任意 | 最大200文字。Web検索のみ空欄を拒否 |

材料で両欄が空の行、空白だけの手順は保存前に除外する。分量のみの行は材料名を要求する。残る行の上限超過や不正値は勝手に切り捨てず、その欄にエラーを表示する。人数・時間は小数、負数、非数、無限大を拒否。料理名だけでも保存可能とし、後から補完できる。

保存処理中は二重送信・画面離脱を抑止する。成功時に短い完了メッセージを表示して詳細へ移動。失敗時は入力・写真のプレビューを保持して再試行できる。強制終了・OSによるプロセス破棄まで未保存入力の保持は保証しない。未保存入力の自動永続化は初期版に含めない。

## 3. レシピブック（R01〜R05）

| ID / 機能 | 入力・操作 | 出力 | 例外・受け入れ条件 |
| --- | --- | --- | --- |
| R01 新規登録 | 手入力・貼り付け・画像・URLを編集画面に設定し保存 | UUIDを持つレシピと添付 | 必須違反では保存しない。成功後の再起動でも内容と画像が一致する |
| R02 編集 | 既存レシピを編集して保存 | ID・登録日を維持し、更新日とrevisionを更新 | キャンセル時はDB不変。競合時は上書きせず再読み込みを案内。失敗時に既存写真を失わない |
| R03 削除 | 詳細のメニューから削除、料理名と関連削除件数を確認 | レシピ・添付・その調理履歴・決定履歴をまとめて削除 | キャンセルで不変。失敗時は全件保持。成功後は一覧へ。ごみ箱・取り消しはなし |
| R04 一覧・絞り込み | カテゴリ、タグ、お気に入り、検索語、並び順を指定 | 条件に合う写真付きカードと件数 | 条件はAND。0件は条件解除と登録の導線。画像なしでもカードを表示 |
| R05 定番 | 星ボタンを操作、定番画面を開く | お気に入りだけの一覧 | 保存完了後に表示確定。失敗なら元状態を保持。定番画面で解除するとカードを外し、完了を通知 |

R04の既定は更新日時の降順。同時刻はID昇順で固定する。選べる並び順は「更新が新しい」「料理名」（日本語照合、同値はID順）。カードは写真、料理名、カテゴリ、調理時間、星、タグ最大2個と残数を表示する。最終調理日は履歴から導出し、Phase 2で追加する。

検索対象は料理名、材料名、タグ、メモ。NFKC・小文字化・前後空白除去で比較し、空白区切りの各語が対象フィールドのいずれかに部分一致すればよい（語どうしはAND）。かな/カナ・同義語・表記揺れの自動対応は初期版では行わない。タグ絞り込みは正規化後の完全一致で、複数タグはすべて含むもの。検索語空欄は全件。日本語IME変換中は検索更新しない。

一覧はまず30件を表示し、「さらに表示」で30件ずつ追加。レシピのテキストは端末メモリ内で検索し、画像Blobは表示対象だけ読む。戻る操作では検索条件・表示件数・スクロール位置を同一セッション内で維持する。初期版の上限は1,000レシピとし、それ以上は削除または設計見直しを案内する。

## 4. 登録方法（R06）

登録画面は共通の1画面とし、入口によって写真選択・URL欄などへフォーカスする。

- 手入力：料理名から入力。必須は料理名とカテゴリのみ。
- 料理写真：端末の画像選択、または「撮影」からカメラ入力。自動解析せず、料理名などは利用者が入力する。
- スクリーンショット：添付種別を「スクリーンショット」にして画像保存。詳細で拡大し読める。本文への変換はしない。
- URL保存：料理名とURLを手入力。URLを貼り付けてもタイトル・本文・OGP・画像を自動取得しない。
- コピー登録：「材料をまとめて貼り付け」「手順をまとめて貼り付け」を用意。改行で空でない行へ分割し、材料は行全体を材料名、分量を空欄としてプレビューする。手順は1行1手順。利用者が修正して「追加」を押すと末尾へ追加する。既存入力は消さない。貼り付け1回20,000文字まで、結果は共通上限で検証する。

受け入れ条件：5つの入口で同じレシピ型へ保存できる。貼り付けのプレビューでキャンセルすれば元のフォームは不変。HTMLやスクリプトが含まれても文字として扱い、ネットワーク送信しない。

## 5. Web検索・URL利用（R07）

「レシピ検索」は「保存済み」「Webで探す」の2タブ。Webは料理名・食材を1つの欄へ入力し、「Webで検索」で `https://www.google.com/search?q=` に `encodeURIComponent(入力 + " レシピ")` を付けたリンクを開く。検索サービス選択設定は初期版に含めない。

入力は1〜200文字。出力は外部ブラウザの検索画面であり、アプリ内には検索結果を取得・表示しない。検索語が検索サービスへ送信されることを欄の近くに示す。OS・ブラウザの判断で別タブやブラウザ画面になるため、特定の外部アプリの起動は保証しない。ユーザー操作と直接結び付いたリンクを使う。

利用者は外部でURLや必要情報をコピーし、アプリへ戻って「URLから登録」へ貼り付ける。クリップボードの自動読み取りやAndroid共有先としての受信は初期版対象外。オフラインと判定した場合はWeb検索を無効化し、保存済み検索を案内する。オンライン表示でも接続成功は保証しない。リンク先障害は外部ブラウザで扱い、アプリ内データは変えない。

受け入れ条件：日本語・`&`・`#`入りの語を安全にエンコードできる。URLだけ保存したレシピの外部本文はオフラインでは読めないことを表示する。自動取り込みの境界は[ARCHITECTURE](ARCHITECTURE.md)に従う。

## 6. 献立ルーレット（R08〜R10）

### 条件と抽選単位

1回に1品を選ぶ。主菜・副菜・汁物をまとめて献立セットにする機能は将来。カテゴリ選択は「すべて」「主菜」「副菜」「汁物」（その他のカテゴリも選択可能）。初期値は「すべて」。お気に入り限定は初期OFF、タグは未指定。

「最近作った料理を除く」は初期ON・7日、選択肢はOFF / 3 / 7 / 14 / 30日。抽選時の端末ローカル日付をDとし、N日なら `D-(N-1)〜D` の調理日を持つ料理を除く。7日は今日を含め7暦日で、日付計算は24時間のミリ秒減算にしない。決定しただけの料理はこの除外条件に含めない。

### R08 抽選・再抽選アルゴリズム

1. 最新の保存データへカテゴリ・お気に入り・タグ・調理日の条件をすべて適用し、候補集合Cを作る。
2. 0件なら抽選不可。「候補がありません」と件数・条件解除の操作を表示する。条件を自動で緩めない。
3. 1件なら即時表示し「候補は1件です」。再抽選を無効にして「これに決定」は可能。
4. 2件以上なら直近に決定したレシピID（最新の決定履歴1件）を除外する。残りが0件の場合だけ除外を適用しない。
5. 再抽選では現在表示中のIDも除く。ただし0件になるなら手順4の除外を解除してCから現在のIDだけを除く。これで候補2件なら再抽選で必ず変わる。
6. 残る候補をID順へ整列し、`floor(random() * 件数)` で一様抽選する。`random` は0以上1未満の乱数を返す関数でテスト時に差し替え可能にする。

表示しただけの結果は履歴へ保存しない。重み付けやAIは使わない。全期間の偏りを数学的に保証するものではなく、最近の調理・直近決定・連続表示の除外で単純に偏りを軽減する。

条件変更、レシピ変更通知、日付が変わった状態での再操作では候補を再評価し、古い結果を無効化する。再読み込み・画面離脱で未決定結果は破棄する。

### R09 「これに決定」

入力は表示中のレシピIDと操作ID。最新候補にまだ含まれるか再検証し、決定時の料理名・カテゴリのスナップショットと決定日時を保存する。保存完了後に「今日の候補に決めました」を表示、ボタンを無効化する。連打・保存再試行では同じ操作IDを再利用して二重登録しない。別の抽選開始で新しい操作IDを発行する。

失敗時は結果を保持し再試行可能。削除済み・条件不適合なら保存せず再抽選を案内。受け入れ条件：1操作が1履歴になる。決定だけで調理履歴や最終調理日は変化しない。

### R10 調理履歴

詳細またはホームの決定履歴から「作った」を選び、調理日と任意メモを入力して保存。過去日も登録可能。決定履歴から登録した場合はその決定IDを紐付け、1決定に調理履歴は最大1件（再操作は既存履歴の編集へ）。詳細からの手動登録は同じ料理・同じ日で複数件を許可する。

履歴は新しい調理日順、同日は登録日時降順、最後にID順。編集で日付・メモを修正でき、削除は確認後に実行する。調理履歴を消しても決定履歴は消さない。決定履歴の取消は確認後に削除し、紐付く調理履歴の決定IDだけをnullへ変更する。実際に作った記録は残す。

受け入れ条件：履歴の追加・修正・削除が最終調理日と次回抽選に反映される。日付変更があっても記録済みの調理日文字列は変わらない。

## 7. 写真・容量（R11）

| 項目 | 採用初期案 |
| --- | --- |
| 受入形式 | JPEG / PNG / WebPの静止画。拡張子だけでなく内容と復号結果を確認。SVG / GIF / HEIC / 動画は非対応と説明 |
| 入力上限 | 1枚20MiB、40メガピクセル、いずれかの辺16,384px以内。画像ヘッダの寸法を確認してから復号 |
| 料理写真 | 縦横比維持・拡大なし、長辺最大1,600px、JPEG品質0.8から開始、保存後最大1MiB |
| スクリーンショット | 長辺最大2,560px、まずPNG、1MiBを超えるとWebP品質0.9を試す。文字の可読性をプレビューで確認 |
| 再圧縮 | 1MiB超過なら品質を段階的に下げる（JPEG 0.7/0.6、WebP 0.8/0.7）、なお超過なら辺を0.8倍ずつ最小長辺640pxまで縮小。収まらなければ拒否して切り抜き等を案内 |
| サムネイル | 料理写真のみ、長辺最大320px・拡大なし、JPEG、最大100KiB。上限まで再圧縮。元画像を直接カードで読まない |
| 表紙 | 利用者が料理写真から1枚選ぶ。未選択なら最初の料理写真。スクリーンショットを表紙にしない |

端末内で1枚ずつ処理し、向きを正してCanvas等で再エンコードする。透明背景は料理写真で白へ合成。元ファイルを保存しない。処理結果をプレビューで確認して保存する。料理写真・スクリーンショット合計6枚、表紙削除時は残る最初の料理写真へ切替、なければプレースホルダにする。画像変更・削除はフォーム保存で確定し、キャンセルなら元に戻る。

圧縮・カメラ起動・形式の非対応は理由を表示し、通常のファイル選択や画像なし登録へ戻れる。画像処理失敗を理由にテキストを消さない。画像だけを送信する外部サービスは使わない。

総量・バックアップの上限は[DATA_MODEL](DATA_MODEL.md)を正本とする。設定画面にアプリの画像容量・件数と、取得できる場合はブラウザ全体の使用量/割当量の概算を表示する。ブラウザ割当量の80%以上、またはアプリの画像上限の80%以上で警告する。自動削除はしない。容量不足時は写真削減、不要レシピ削除、バックアップを案内し、ブラウザデータ全消去を復旧策にしない。

## 8. バックアップ・復元（R12〜R14）

| ID | 入力・操作 | 出力・受け入れ条件 | 例外 |
| --- | --- | --- | --- |
| R12 出力 | 設定から「バックアップを書き出す」 | レシピ・添付・決定/調理履歴を含む単一JSON。出力時点の整合したスナップショット | 生成失敗時はDB不変。ダウンロード要求完了は端末外保管完了ではない |
| R13 復元 | ファイル選択→全件検証→件数/日時の比較→全件置換確認→実行 | 正常ファイルを原子的に復元。新規端末でも写真・履歴・お気に入りを再現 | 不正、未来バージョン、容量不足、中断は既存データを保持。部分復元しない |
| R14 保存領域管理 | 容量表示、永続保存の許可要求、バックアップ案内 | APIがなくても基本機能とバックアップを利用可能 | 許可拒否でも利用を続けられる。永続性を保証したと表示しない |

復元は**全件置換のみ**。IDでのマージ・追加インポートは将来。「現在のデータは置き換わります」を表示し、現在と復元後の件数を示す。先に現状を書き出す操作を用意し、「バックアップ済み、または置換を理解した」のチェックと「置き換えて復元」の押下を必要とする。確認のキャンセルは一切変更しない。復元中は編集・追加・削除を無効化する。操作完了後はホームへ戻り、古い一覧キャッシュ・未決定結果を破棄する。

バックアップ未出力、または最終出力要求から7日以上経過しデータ変更がある場合、ホームと設定に閉じられる案内を出す。空DBでは案内しない。初回登録後に消失リスクを1度案内し、設定で常時読めるようにする。端末故障に備え、書き出したファイルを端末外へ保管することを勧める。自動クラウド送信はしない。

## 9. オフライン・例外（R15〜R16）

R15：初回オンライン起動でアプリの必要ファイルのキャッシュが完了し、Service Workerに制御された後、機内モードで再起動して保存済みレシピ・写真の閲覧、検索、編集、ルーレット、バックアップ・復元を利用できる。初回アクセス自体のオフライン動作は保証しない。外部検索、元サイト閲覧、アプリ更新には通信が必要。

R16：DBを開けない場合は「データを読み込めません」と再試行を表示し、空のレシピ一覧と誤認させない。自動初期化はしない。更新中や別タブの競合は理由と再読み込みを示す。未知のレシピIDは「見つかりません」と一覧への導線。エラー表示には失敗した操作・データが保存されたか・次の操作を含め、写真・本文などの私的内容をログへ書かない。

## 10. 初期版に含めないもの

自動スクレイピング、JSON-LD自動取得、公式API連携、OCR、AI解析、推薦AI、買い物リスト、家族共有/同期、ログイン、複数端末競合解決、栄養計算、人数による自動分量換算、週間献立セット、通知、バックアップ暗号化は将来。検討時は[DECISIONS](DECISIONS.md)を更新し、費用・外部送信・互換性への影響を確認する。
